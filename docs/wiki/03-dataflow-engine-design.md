# 03 — Dataflow engine design (row tokens, line buffers, DSP packing)

The 52-node frozen graph (worksheet.py `conv_layers()`) runs as one long
dataflow pipeline: one HLS engine per node, chained by `hls::stream` row
tokens. The transport contract is `hls/common/mgr1_stream.h`:

- Token = one full feature row, all channels interleaved (HWC row):
  `struct RowTok { int w; i8_t px[GR_MAX_W]; }`.
- Every engine has compile-time bounded storage (no dynamic allocation in
  the synthesizable path) and the same access pattern in C-sim and RTL.
- In csim the tokens run through `mgr1::fifo` (plain ring); under Vitis HLS
  2024.2 the same source maps to `hls::stream` and the cascade becomes a
  dataflow region.

## Per-node engine shape

Stem: 3x3 s2 pad 1, 3 -> 32.  Every engine: bias -> MAC over (cin, ky, kx)
in the frozen order -> per-channel requantize -> int8 saturate. Exact
per-layer unroll table: `docs/09a-unroll-plan.md` (generated by
`tools/gen_unroll_plan.py` from the worksheet; never hand-edit it).

## DSP budget: why U is capped at 8

The xck26 carries 1,248 DSP48E2s; two packed INT8 MACs per DSP give a hard
ceiling of 2,496 MACs/cycle across the whole array. The unroll plan gives
each engine `U <= 8` pixels-in-flight and keeps the sum over co-resident
engines inside the budget, so several engines reuse the array across the
dataflow schedule instead of one engine hogging it.
